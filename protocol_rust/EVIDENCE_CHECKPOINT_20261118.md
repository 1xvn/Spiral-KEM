## Evidence differences and missing observations

- The original mathematical specification gives a whole-message log2 bound near −1855.06 from coefficient probabilities. The six-candidate package gives −1850.14 for baseline A using a Chernoff bound. Both use idealized sampling. Their methods and the actual seeded implementation must remain identifiable.
- Preparation records have narrower scope than later operator submissions. The [wire preparation archive](evidence/wire_stall_runner_20261118/) covers a short local release. The upload above adds cross-host release and server-local expiry. Likewise the [committed load run](evidence/load_20261111/) is one local 30-minute run on a dirty checkout whose selected bytes were subsequently matched to `04ce7d7`. The twelve uploaded platform archives have their own revision and raw probe streams. For example, the 24-hour originals are `Spiral-load-oci-aarch64-24h-20261113T114256Z-118387.tar.gz` (SHA-256 `f0f0937500a3af7be946e65ed2f117e8826830adb60786e47caedec35cbc147d`) and `Spiral-load-wsl-x86_64-24h-20261114T062743Z-2397.tar.gz` (`875aa996945b6ef473c1e280c643250cfb5d507c85134ecea33711d1c73b22f7`). Each contains `probe.stdout.jsonl`, `resources.jsonl` and source snapshots.
- Of the two cross-host uploads at `557ea34`, the one ending in `3710641008480` contains only a normal case. The one ending in `4014323944008` contains all four cases. Their shared overall pass label has different coverage.
- The [initial CI failure](../ci/local_ci_20261107/initial_failure/result.json), [sandbox LSan failure](../native_research/evidence/fuzz_platforms_20261107/sandbox-lsan-failure/result.json) and [recovery formatting error](evidence/key_recovery_20261110/recovery-format-error.json) retain their original verdicts. Short operations on both hosts recorded exit 1 for interruption and RSS/FD/thread guard cases by design. A successful clock collection by itself provides no WSL timing calibration.
- The ordinary server already accepts multiple sessions using a shared admission object and a Tokio task per socket. Its diagnostic CLI explicitly requires one connection for wire stall. The gate handles one client, and the current controller resumes as soon as that single-session witness arrives. The ordinary four-session result has no stall marker. Across the inspected implementation, operators and original results, there is **no implementation or execution receipt for one stalled plus three healthy sessions on the same server**. ## Next implementation contract · one stalled connection and three healthy connections

**Question.** While one authenticated session has an observed, sustained TCP write stall, can all three existing healthy sessions exchange distinct authenticated application messages on the same OCI server?

| Condition | Required evidence for a pass |
| --- | --- |
| Prerequisites and topology | Matching selected source hashes on WSL x86-64 and OCI ARM64, feature-enabled release binaries, valid temporary test pin/CA, authorized SSH forwarding and free loopback test ports. One owned server process, listener, admission object and worker pool. Exactly four authenticated sessions on that listener. Route only the selected session through the gate. Keep the other three on the ordinary data path. Preserve the per-IP cap of four and existing deadlines. |
| Identity and overlap | Establish all four and hold them open. Match each client's session ID, exporter binding and transcript with the server. Require all four sessions to have distinct values for each identifier. Record the server process identity and admission active=4, pending=0. Assign roles through authenticated test messages and identity matching, independently of accept order. |
| Before and during the stall | Gate only the selected connection after its baseline. Require the existing OPEN, below-TLS write-Pending, incomplete bulk and stable byte-count witness for at least 200 ms. Once the controller receives that witness, authorize the three healthy peers to send session-specific challenges. Each must verify ten ordered 1,024-byte echoes before any gate resume. Hold the healthy sessions open at the barrier. |
| Causal proof | Record a second snapshot on the same stalled session **after** all three clients acknowledge their last challenge and **before** sending the resume command. Require unchanged written-byte and gate-read counters, write still pending, gate still held, and four active sessions. Use controller barriers, per-peer sequence numbers and raw events for ordering. Wall-clock alignment between hosts cannot establish overlap. Reject missing, reordered, duplicated or mismatched witnesses. |
| Release and cleanup | Resume once, verify all 1,021 bulk messages plus the three baseline messages, and require authenticated CLOSE for all four sessions. Record endpoint outcomes, returned buffers, joined I/O tasks, zero live KEM keys, server admission active/pending zero and owned listener/child teardown. Preserve partial logs and the failure reason if any criterion fails. |
| Budget | One release case per operator run. Stalled payload at most 16 MiB of server DATA, plus control and TLS framing. Allow up to 10 s for healthy progress after the witness and 120 s overall including teardown, excluding build and SSH preparation. No timeout replay or soak is needed to answer this question. |
| Deliverable | Add a diagnostic-only mixed-session controller and event checks. Reuse the existing ordinary handler, TCP observer, gate and packaging helpers. First exercise the contract with short local positive and negative checks, including a healthy echo arriving only after resume. Then the operator runs one WSL-to-OCI case. Collect client/server/controller JSONL, process exit codes, before/after source and binary identities, per-case verdict and SHA-256 inventory in one WSL archive. Report implementation, local verification and operator execution separately. |
